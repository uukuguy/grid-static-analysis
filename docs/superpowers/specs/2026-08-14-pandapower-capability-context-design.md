# Pandapower 全能力连续分析上下文设计

- 日期：2026-08-14
- 状态：待用户书面审阅
- 适用命令：`grid-agent analysis`
- 依赖设计：
  - `2026-08-12-pandapower-semantic-capability-redesign.md`
  - `2026-08-14-continuous-analysis-context-design.md`
- 取代：`2026-08-14-contextual-analysis-without-policies-design.md`

本设计修订连续上下文规格中“只投影当前能力白名单字段”和“记录版本化 policy 标识”的约定，也修订语义能力规格中把 `policy-risk` 当作默认发布规则来源的部分。风险评价仍可作为语义能力存在，但只能消费来源明确的模型约束、用户判据或已命名标准。

## 1. 决策与纠偏

`analysis` 是一次运行内的单一连续会话。后续指令必须根据当前活动模型、前序仿真结果、已验证事实和会话历史解释，不能退化成逐题独立问答。

连续上下文不是现有题集的流程状态，也不是几个固定答案的缓存。它是 pandapower 语义能力在一次分析运行中的统一状态投影。`docs/TASK.md` 和验证问题只用于验收，不定义系统能力边界，也不得生成题目专用分支。

现有 `AnalysisContext v1` 的事件账本、来源引用和确定性归约仍然有价值，但它只完成了控制面和溯源内核，没有完整表达 pandapower 领域状态。本设计补上能力目录、模型语义、工况、计算生命周期和结果适用性，并删除早期 `static-analysis-v1` 对答案语义的干预。

## 2. “全能力覆盖”的准确含义

全能力覆盖分为两个层次：

1. **架构覆盖**：上下文模型能够一致表达 pandapower 各能力族的前置状态、调用、产物、状态变化、适用范围、失败与可用性。该要求立即成立。
2. **发布覆盖**：项目逐步实现并发布具体语义能力。未发布能力必须明确标记为 `not_published`，不得伪装成模型缺少数据、仿真失败或智能体“执行限制”。

本设计不要求一次性把 pandapower 3.4.0 的每个 Python API 暴露给模型。项目仍通过稳定的电力系统语义能力提供功能，不暴露原始 `pandapowerNet`、DataFrame、任意 Python、文件或 shell。

首轮改造聚焦当前已发布的只读静态分析能力，但数据模型和扩展接口必须适用于以下能力族：

- 注册模型、不可变修订、网络元数据和元素语义；
- 拓扑、连通性、开关状态和图分析；
- AC/DC 潮流、初始化、求解配置和收敛诊断；
- 结果查询、汇总、排序、比较和派生指标；
- 故障或元件停运场景、N-1 与批量场景分析；
- OPF 及其目标、变量、约束和可行性；
- 短路计算；
- 状态估计和量测；
- 时序、控制器及输出结果；
- 将来的模型创建、导入和修改所产生的不可变修订。

## 3. 权威边界

### 3.1 pandapower 与 gridctl

pandapower 3.4.0 是计算引擎。`gridctl` 通过 `grid-capability` 1.0 提供项目定义的语义能力，负责网络数据读取、确定性计算、完整结果和证据。任何网络特定或数值结论都必须来自该边界。

### 3.2 AnalysisContext

`grid-agent` 维护 AnalysisContext。它只接纳经过验证的 gridctl 工具结果和控制器事件，记录当前可用状态及其来源，不重新计算电气量，也不把模型文本提升为已验证事实。

### 3.3 对话历史

Pi 会话提供语言连续性，帮助理解代词、省略主语和用户目标，但不作为仿真事实的权威来源。结构化上下文与会话历史共同参与理解；涉及网络和数值时，以结构化上下文所引用的 gridctl 产物为准。

## 4. 四层结构

### 4.1 上下文内核

保留追加式事件账本、纯归约器、状态版本、状态哈希、turn 归属、证据引用和可重放能力。内核只负责“什么状态在何时由什么事件产生”，不内置具体题目和 pandapower 函数名。

### 4.2 能力目录

每个语义 capability contract 增加可机器验证的上下文声明：

```json
{
  "capability": "powerflow.ac.run",
  "availability": "published",
  "requires_state": ["model.active_revision"],
  "consumes_state": ["model.operating_state", "solver.profile"],
  "produces_state": ["calculation.powerflow"],
  "invalidates_state": [],
  "result_kind": "powerflow.ac",
  "context_projector": "powerflow-ac-v1"
}
```

能力目录区分：

- `published`：当前运行时可调用；
- `not_published`：pandapower 支持但项目尚未提供语义能力；
- `not_applicable`：能力已发布，但不适用于当前模型或状态；
- `unavailable`：应可用但运行时依赖缺失；
- `failed`：能力实际调用后失败。

这些状态不能混称“执行限制”。报告必须使用具体原因。

### 4.3 领域状态

AnalysisContext 增加可扩展的 `domain_state`，其核心分区为：

```json
{
  "model": {},
  "operating_state": {},
  "scenarios": {},
  "calculations": {},
  "constraints": {},
  "capabilities": {},
  "artifacts": {}
}
```

- `model`：活动模型和修订、来源、元素规模、标识命名空间、拓扑或参数状态摘要；
- `operating_state`：当前开关/在运状态、负荷与发电设定、已选工况及其修订关联；
- `scenarios`：基础场景和派生场景、变更集、父场景、状态及结果关联；
- `calculations`：按结果引用登记的计算类型、输入状态、求解器、收敛或可行性、适用模型/场景和结果摘要；
- `constraints`：模型数据、用户输入或计算任务中显式存在的约束，必须包含来源和作用域；
- `capabilities`：能力族和具体能力的发布、适用与运行时状态；
- `artifacts`：完整结果、证据和工具输出的位置与完整性，不把大表复制进上下文。

所有领域状态记录都带 `context_ref`、`revision_ref`、可选 `scenario_ref`、生产 capability、生产 turn 和来源引用。结果不得脱离其输入模型、场景和求解配置被复用。

### 4.4 面向智能体的上下文视图

每题开始前注入一个有界、可读、控制器生成的视图，至少显示：

- 当前活动模型、修订和工况；
- 当前指令可用及不适用的能力族；
- 已有计算结果及其模型、场景、有效性和可复用条件；
- 相关模型约束及来源；
- 前序已验证事实和答案摘要；
- 尚未解决的具体问题。

完整结果留在 artifacts 中，通过专用、分页或聚合型语义工具按需读取。压缩只能减少模型视图，不能删除结果，也不能丢掉数值的来源与适用范围。

上下文视图的选择依据是 capability contract 中声明的语义类型、活动模型和依赖关系，不使用题号、固定问句或关键词答案表。

## 5. 通用状态流转

每次能力调用按同一流程进入上下文：

1. 根据 capability contract 检查活动模型、场景和前置计算；
2. gridctl 执行语义能力并先持久化完整结果；
3. 验证内容引用、模型修订、场景和 capability 身份；
4. 对应 `context_projector` 生成紧凑领域状态事件；
5. 归约器更新 `domain_state`，保留旧状态和来源链；
6. 后续指令通过类型和依赖关系发现可复用结果；
7. 报告从相同事件和 artifacts 投影人类可读结论与详细轨迹。

打开另一个模型或产生新修订时，旧结果不会消失，但不再属于活动状态。后续调用只有在 capability contract 明确允许且模型、修订、场景和求解配置相容时才能复用。

## 6. 连续语言语义

省略模型名的后续指令默认继承当前活动模型。例如第一题打开 IEEE-39 后，第二题中的“母线”指 IEEE-39 母线，除非用户明确改变对象。

这种继承不是从固定题目推断，而是从以下通用状态解析：

- `model.active_context_ref`；
- 最近明确选定的元素、场景或结果；
- 当前 turn 的消耗引用；
- capability 的输入语义和适用范围；
- 对话中的明确覆盖指令。

当存在两个同样合理的活动对象且无法由结构化状态消歧时，智能体应提出简短澄清；不得静默选择，也不得调用无关 policy 填补歧义。

## 7. 约束、标准与 Policy

`configs/policies/static-analysis-v1.json` 是早期发布规则遗留，不是 IEEE-39 模型事实，也没有足够来源成为通用行业标准。它以及 `analysis.policy.describe` 不再参与解题、上下文投影或答案验证。

上下文只承认来源明确的约束：

- 模型中显式提供的约束，例如适用元素的 `min_vm_pu`、`max_vm_pu`；
- 用户在当前分析中明确指定的判据；
- 某项已命名标准通过独立、可引用知识来源引入的判据；
- 某个计算任务自身的参数或可行域。

约束记录必须包含 `source_kind`、`source_ref`、适用模型/元素/场景、数值与单位。没有约束时仍可报告潮流值、极值和排序，但不能生成“低压”“高压”“越限”“正常”等判断。

### 第二题的通用处理

第一题已经激活 IEEE-39 后，“母线电压正常运行范围是多少”首先查询活动模型的母线电压约束：

1. 若模型显式定义，回答数值、作用范围及模型来源；
2. 若用户或已命名标准在本会话中定义了判据，明确按该判据回答；
3. 若都没有，回答“当前 IEEE-39 模型未定义正常运行边界”，必要时补充实际潮流电压范围，但不能凭空把实际极值解释为正常范围。

这是一条适用于所有模型和约束问题的语义规则，不是第二题专用处理器。

## 8. 错误和诊断语义

以下情况必须分别表达：

- 模型没有某项数据：`model_data_absent`；
- 项目尚未发布该 pandapower 能力：`capability_not_published`；
- 能力不适用于当前模型或场景：`capability_not_applicable`；
- 缺少必要的前置计算：`prerequisite_missing`；
- 求解器不收敛或问题不可行：使用对应计算诊断；
- 证据或上下文投影异常：记录 advisory diagnostic，保留已提交答案和原始工具结果；
- 智能体没有给出答案：只有此时才形成 turn 失败。

审计和上下文投影不得因为内部引用错误覆盖已有的有效回答。报告展示回答、主要依据和过程；长引用保留在详细轨迹和 artifacts 中。

## 9. 实施边界

首轮实施只改造当前已发布路径：

- 移除 `static-analysis-v1` 配置、工具、提示、离线知识和验证捷径；
- 给 capability contract 增加统一状态声明和 availability；
- 将现有模型打开、元素查询、拓扑、潮流、结果分析和 N-1 输出投影到通用 `domain_state`；
- 增加模型约束的通用语义查询和上下文投影；
- 让 turn 注入视图包含活动模型、领域状态摘要、结果适用性和能力状态；
- 更新报告，使上下文变化以人类可读方式展示，并链接完整轨迹。

OPF、短路、状态估计、时序和模型修改本轮不新增执行工具；它们先进入能力目录，以 `not_published` 说明当前边界。后续新增能力必须复用同一 capability contract 和上下文事件机制，不修改 AnalysisContext 顶层结构，也不添加题目分支。

## 10. 验收标准

- 已知题目文本、题号和答案不出现在运行时分支或上下文投影逻辑中；
- 同一连续运行中，后续指令能继承活动模型、场景和已验证结果；
- 切换模型后，旧结果仍可追溯但不会被误用为新模型结果；
- 每个已发布 capability 都声明前置状态、产出状态、result kind 和 projector；
- 能力目录能区分已发布、未发布、不适用、不可用和调用失败；
- 上下文能表达当前已发布静态分析路径，并能在不改变顶层模型的情况下扩展到其他 pandapower 能力族；
- 不再存在 `static-analysis-v1` 或 `analysis.policy.describe` 的已发布运行时路径；
- 没有来源明确的约束时，不产生正常、越限或风险评价；
- IEEE-39 连续问题中的电压范围从活动模型约束语义处理，不走离线知识捷径；
- 完整数值结果和证据保存在 artifacts，模型视图和报告只做可追溯的有界投影；
- 投影或审计故障不会覆盖已经提交的回答；
- 单元、端到端、离线验证和脚本化连续分析均覆盖跨 turn 状态继承及 held-out 表达，不只覆盖当前九题。

## 11. 不做事项

- 不开放任意 pandapower、pandas、Python、文件或 shell 能力；
- 不把完整结果表塞入提示词；
- 不在本轮实现跨运行 resume、会话切换或并发 turn；
- 不用模型自由文本修改权威上下文；
- 不把 pandapower 默认值、项目配置或常见经验值自动宣称为模型约束或行业标准；
- 不为验收问题建立固定工作流、固定答案或隐式 policy。
